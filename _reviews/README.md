# `_reviews/` —— 结论落盘（共享黑板的读端）

**规矩：谁的结论写谁的名字文件，原始产物不经过任何人手转述。**

## 命名

```
_reviews/<agent>-<任务卡slug>.md
```

例：`_reviews/cc-review-collab.md`、`_reviews/dsh-review-collab.md`

- **不覆盖**。同一张卡派多轮就写多份（`dsh-review-collab-r2.md`），因为"改一版再审一次"本身是证据。
- **不合并**。一致项合并会让人看不出谁和谁本来就不一样。

## 每份结论必须带

| 项 | 为什么强制 |
|---|---|
| 署名（哪个 agent / 哪一轮） | 不署名没法判断结论的来源 |
| 读了哪些文件 | 自述不是轨迹，但没读过就说不出细节 |
| 每条结论带 `文件:行号` | 抽查的最小单位 |
| **每条数字带算式** | 审稿人也留过不准确，数字必须能被复核 |

## 这目录存在的意义

以前结论只活在对话里，你看到的是**我的话**。
放在这里，你可以：

1. 直接打开看它到底说了什么（**包括我说错的部分**）；
2. 对着仓库代码核它的每一条；
3. 在我不在场的时候，自己派新一轮审稿。

## 已知坑（踩过才知道的）

- **AI 自报"我写好了"不是事实** —— 必须校验字节数。
  `< 500 B` = 只有 CLI 噪音、根本没跑起来；`> 2 KB` = 真的拿到产出。
- **别看任务状态** —— `Status: failed` 时日志可能 51KB 完整，
  判据永远是"日志里有没有真内容"。
- **每份结论都可能含不准确数字** —— 这轮就抓到审稿人把 218（块总长）说成单行长度、
  把 271（切分产出）说成 263（过关入库）。⇒ 数字一律按"待核"处理。
