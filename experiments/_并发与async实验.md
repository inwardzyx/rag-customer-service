# 实验：并发与 async —— 瓶颈到底在哪

**跑法**：
```bash
# 1) 起服务（要能连上 DeepSeek，或用假 key 看失败路径的耗时）
python -m uvicorn service:app --port 8077
# 2) 跑压测
python experiments/concurrency_bench.py --n 10
```

---

## 一、先说这个实验想回答什么

不是"async 快不快"（这个问题本身是错的），而是**"瓶颈在哪"**。

原因：`/chat` 是同步 `def`，FastAPI 会把它丢进线程池 —— **同步服务本来就能并发**。
所以"并发比串行快"这件事，不需要 async 也能做到。数字漂亮，结论错误。

---

## 二、成本结构（这组数是整个实验的地基）

同一个问题，分段计时（实测，2026-10-10）：

| 环节 | 耗时 | 性质 |
|---|---|---|
| `search()` 本地混合检索 | **8 ms** | CPU 计算 |
| `rerank()` 调 DeepSeek | **2434 ms** | **等网络** |

⇒ **99.7% 的时间在等网络，0.3% 在算。**

★ 这一组数字比"async 快 10 倍"值钱得多，因为它解释了**为什么**这类服务适合异步：
"async 不让程序变快，它是让等待期间的 CPU 空出来。"
判断一个服务该不该上 async，**先看成本结构**——等网络占比高就适合，纯 CPU 计算就没用。

---

## 三、并发实测

| 场景 | 墙钟总耗时 | 平均单请求 |
|---|---|---|
| 串行 10 次 | 20.48 s | 2048 ms |
| 并发 10（同步服务 + 线程池） | 2.05 s | 2035 ms |
| 并发 3 / 5 / 8（分别） | 2.11 / 2.13 / 2.16 s | 2094 / 2111 / 2135 ms |

**要读的三个结论：**

1. **单请求耗时几乎不变（2048 → 2035 ms，差 1%）**
   ⇒ **async 不会让单个请求变快。** 这是最常见的误解。

2. **并发提升 9.98 倍 —— 但这是线程池给的，不是 async 的功劳**
   ⇒ 要证明 async 有用，得再拿一个真 async 版对比（"单进程、不靠多线程"的收益）。

3. **并发 3 到 8 线性增长、没有拐点**
   ⇒ 说明这条路径上**没有排队**（见下一节，我一开始判断错了）。

---

## 四、★ 我犯的两个错，记下来

### 错误 1：拿"并发快 9.98 倍"当成 async 的功劳

数字是真的，归因是错的。**同步 `def` + 线程池本来就能并发。**
如果当时直接把这句话写进简历，就是"用漂亮数字包装了一个不存在的结论"。

⇒ 纪律：**先问"这个收益是谁给的"，再报数字。**

### 错误 2：断言 `LLM_POOL max_workers=4` 是瓶颈，被自己的实测推翻

我看代码看到 `_LLM_POOL = ThreadPoolExecutor(max_workers=4)`（`service.py:150`），
就推断"超过 4 并发会排队"。实测并发 3/5/8 **全部线性增长，没有拐点** —— 推错了。

**为什么错**：这个判断依赖一个未经检验的前提 —— "请求会走到 rerank"。
DeepSeek Harness 读代码后指出（`service.py:181` submit → `:183` result），
401/402 是**提交之后**才失败的，**不涉及构造期**；我的实测则显示每个请求 2 秒整返回，
与 rerank 的 2434ms 吻合 —— 说明请求确实走完了整条路径，只是**每次都失败，
所以没有产生排队**。

⇒ 真正的含义：**这个压测只测到了"失败路径很快"，测不出池子满载时的排队行为。**
要测后者需要一个真 key + 慢响应，或者直接把 `max_workers` 改成 1 再压——
**这两件事本次都没做，所以"4 worker 是不是真瓶颈"目前仍未验证。**

⇒ 纪律：**推断出瓶颈后，要设计一个能证伪它的实验**，并诚实标注"这一条还没测出来"。

## 五、面试怎么讲这段（这才是实验的目的）

**❌ 错误讲法**："我用 async 把并发提升到了 10 倍。"

**✅ 正确讲法**：

> 我先量了成本结构：本地检索 8ms、调大模型 2434ms，**99.7% 的时间在等网络**，
> 所以判断这个服务适合异步。
>
> 但压测出来并发快近 10 倍之后，我发现这个功劳是 FastAPI 线程池的——
> 我的端点是同步 `def`，同步服务本来就能并发，**async 并没有额外贡献**。
> 单请求耗时几乎没变（2048ms → 2035ms），变的只是吞吐。
>
> 所以我把结论写成：**async 不是"让程序变快"，是"让等待期间 CPU 空出来"，
> 而且值不值要看成本结构**。纯 CPU 计算的服务，并发再多也提不上来。

★ 后半段"我发现自己的结论错了并纠正"，比前半段的数字更能证明工程判断力。
